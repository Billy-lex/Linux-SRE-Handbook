# HTTP 503 Service Unavailable

## Problem

An HTTP request returns status code 503 Service Unavailable. This means the server (or a reverse proxy in front of the application) is temporarily unable to handle the request. Unlike a 502 (where the backend is unreachable), a 503 usually means the server is alive but is refusing to process the request — typically because it is overloaded, at capacity, or intentionally rejecting traffic.

## Symptoms

- Users see "503 Service Unavailable" in the browser or receive HTTP 503 from API calls.
- The error may be intermittent (appearing under load and disappearing when traffic drops) or persistent.
- The reverse proxy or application logs show 503 responses.
- The service may return a `Retry-After` header, indicating when the client should try again.

## Troubleshooting

### 1. Determine whether the 503 comes from the proxy or the application

```bash
curl -v http://<host>/ 2>&1 | grep -E "< HTTP|< Server|< Retry-After"
```

The `Server` header can reveal whether the 503 is generated by the reverse proxy (e.g., Nginx, HAProxy) or by the application itself. This distinction matters because the troubleshooting path is different:

- **Proxy-generated 503** — the proxy cannot forward the request (no healthy backend, connection queue full).
- **Application-generated 503** — the application is alive but intentionally rejecting requests (overloaded, maintenance mode, circuit breaker open).

### 2. Test the backend directly (bypass the proxy)

```bash
curl -v http://localhost:<backend-port>/
```

If the backend returns 503 directly, the application is the source. If it returns 200 but the proxy still returns 503, the problem is in the proxy layer.

### 3. Check proxy connection and worker limits

For Nginx:

```bash
# Check active connections
ss -tnp | grep nginx | wc -l

# Check worker configuration
grep -E 'worker_connections|worker_processes' /etc/nginx/nginx.conf
```

If active connections are near `worker_connections`, Nginx cannot accept new requests and returns 503.

For HAProxy:

```bash
# Check HAProxy stats (if stats socket is enabled)
echo "show stat" | socat stdio /var/run/haproxy.sock
```

Look for backends in `DOWN` state or session counts near `maxconn`.

### 4. Check if backend servers are marked unhealthy

For Nginx with upstream health checks:

```bash
tail -50 /var/log/nginx/error.log | grep -i "no live upstreams\|upstream.*unhealthy"
```

For HAProxy:

```bash
echo "show stat" | socat stdio /var/run/haproxy.sock | grep -i "DOWN"
```

If all backends are marked unhealthy, the proxy has no server to forward requests to and returns 503.

### 5. Check the application for overload indicators

```bash
# Check application worker or thread count
ps aux | grep <application-name> | wc -l

# Check if the application's listen queue is full
ss -tlnp | grep <port>
```

In `ss` output, look at the `Recv-Q` and `Send-Q` values for the listening socket. A high `Recv-Q` value (close to or at the backlog limit) means incoming connections are queuing up faster than the application can accept them.

### 6. Check application logs for rejection reasons

```bash
journalctl -u <service-name> --since "30 minutes ago" --no-pager
```

Look for:

- **Thread pool or worker exhaustion** — "no available workers", "thread pool exhausted".
- **Connection pool exhaustion** — "connection pool full", "too many connections".
- **Rate limiting** — "rate limit exceeded", "429/503 returned".
- **Circuit breaker open** — "circuit breaker tripped", "fallback activated".
- **Graceful shutdown in progress** — the application is draining connections and refusing new ones (common during deployments).

### 7. Check for maintenance mode or deliberate rejection

Some applications return 503 deliberately during maintenance:

```bash
# Check for a maintenance flag file (common pattern)
ls -la /var/www/maintenance.html
ls -la /etc/myapp/maintenance.flag

# Check Nginx config for maintenance directives
grep -r "503\|maintenance" /etc/nginx/conf.d/
```

### 8. Check system resources

The application may be returning 503 because the system itself is under pressure:

```bash
# CPU and load
uptime
top -bn1 | head -20

# Memory
free -h

# File descriptors (if the application is hitting the FD limit)
ls /proc/<pid>/fd | wc -l
cat /proc/<pid>/limits | grep "open files"
```

If the system is out of file descriptors, the application cannot accept new connections and may return 503.

## Root Cause

Common root causes of HTTP 503:

- **Application overloaded** — traffic exceeds the application's capacity (workers, threads, or connections are all in use).
- **All backends unhealthy** — the reverse proxy has no healthy upstream to forward requests to.
- **Connection queue full** — the application's listen backlog is full and new connections are rejected.
- **Rate limiting** — the application or proxy is intentionally returning 503 to enforce request limits.
- **Maintenance mode** — the service is deliberately returning 503 during a planned maintenance window.
- **Graceful shutdown** — during a deployment, the old instance is draining connections and refusing new ones.
- **Resource exhaustion** — the application has hit a system limit (file descriptors, memory, worker processes).

## Resolution

The fix depends on the identified root cause:

- **Increase capacity** — add more workers, threads, or backend instances:

  ```nginx
  # Nginx: increase worker connections
  worker_processes auto;
  events {
      worker_connections 4096;
  }
  ```

- **Fix unhealthy backends** — restart the failed backend services or fix the health check configuration so healthy backends are correctly detected.

- **Increase listen backlog** — if the application's connection queue is too small:

  ```bash
  # Check current backlog (somaxconn is the kernel-level limit)
  sysctl net.core.somaxconn
  ```

  Increase if needed:

  ```bash
  sysctl -w net.core.somaxconn=4096
  ```

  The application's own backlog setting must also be increased to match.

- **Disable maintenance mode** — remove the maintenance flag file or configuration.

- **Tune rate limits** — if the rate limit is too aggressive, increase the threshold or adjust the window.

- **Increase file descriptor limits** — if the application is hitting the FD limit:

  ```bash
  # Check current limits
  ulimit -n

  # Increase for the service (in the systemd unit file)
  # [Service]
  # LimitNOFILE=65536
  ```

- **Scale horizontally** — add more backend instances behind the load balancer if a single instance cannot handle the traffic.

## Verification

After applying the fix:

```bash
# Test through the proxy
curl -v http://<proxy-host>/

# Test the backend directly
curl -v http://localhost:<backend-port>/
```

Both should return HTTP 200 (or the expected success status).

Check proxy and application logs for continued 503 responses:

```bash
tail -20 /var/log/nginx/error.log
journalctl -u <service-name> --since "5 minutes ago" --no-pager
```

If possible, simulate a moderate load to confirm the fix holds under traffic:

```bash
# Simple concurrency test (use with caution — do not run against production)
for i in $(seq 1 50); do curl -s -o /dev/null -w "%{http_code}\n" http://<host>/ & done; wait
```

All responses should be 200. If any 503 responses appear, the capacity fix was insufficient.

## Prevention

- **Monitor active connections and worker utilization** — alert when connection counts approach configured limits.
- **Set appropriate worker and connection limits** based on expected peak traffic, not just default values.
- **Configure health checks** in the reverse proxy to detect and remove unhealthy backends before they cause 503 for all traffic.
- **Implement graceful degradation** — return a cached or static response instead of 503 when backends are temporarily unavailable.
- **Use autoscaling** in cloud environments to add backend instances when load increases.
- **Load test** the application before going to production to understand its capacity limits.
- **Set `Retry-After` headers** in 503 responses so clients know when to retry, reducing unnecessary retry storms.
